# 复盘卡住时，隔壁那盘棋还能落子吗？

2026-11-25 · PlayRoom 开发笔记 01

A 桌已经下完，玩家请求复盘。B 桌才开局，黑方点下第一颗棋子。假如复盘服务迟迟不回，B 要等吗？

有个看似合理的测试：同时发两个请求，最后看到 A 超时、B 成功。但假如 B 一直排在 A 后面，直到 A 超时才落子，结果也一样。关键证据在两个请求都结束**之前**。

### 把 A 固定在等待的那一刻

实验保留真实的落子接口和 MySQL，只在调用外部复盘的入口放了一个替身。替身先发信号说「A 已经到我这里」，然后停住，等测试放行。这样不用猜哪条线程跑得快。

| 时刻 | A：已结束的对局 | B：刚开始的对局 |
| --- | --- | --- |
| ① | 复盘到达替身，停住 | 尚未落子，版本 0 |
| ② | 仍未放行，复盘请求尚未结束 | 黑方下在 `(7,3)`，HTTP 返回 200；从 MySQL 读到版本 1、一条棋步，坐标相同 |
| ③ | 放行，让替身报告超时；接口返回 `503 MODEL_TIMEOUT` | 再查一次，仍是版本 1、一手棋 |

真正有说服力的是第二行：**B 的棋步已经入库时，A 还不可能返回。** 如果只看棋盘上画出一颗子，或者在放行 A 后才去查库，都少了这条先后关系。

### 这能说明高并发也没问题吗？

不能。这次只测了一个服务实例、两盘棋和一个固定住的外部调用。它排除了「在这条路径上，B 必须等 A 返回才能提交」；没有把服务器的请求线程占满，也没连接真实模型。由此推不出系统吞吐量，更推不出客户端超时意味着远端停止工作。

完整工程的集成测试名为 `GamePersistenceTest.activeGameCommitsBeforeFinishedGamesRemoteReviewIsReleased`。公开仓库另有可以独立复跑的[相关实验](../../backend/playroom-review-contract/src/test/java/dev/playroom/review/BoundedHttpTest.java)：服务器先发响应头和一个字节，再停住，看客户端会不会一直等正文。它回答的是「单次调用等多久」，与「另一盘能否落子」是两个不同的问题。

```sh
mvn -B -f backend/pom.xml -pl playroom-review-contract -Dtest=BoundedHttpTest test
```
